人形机器人全身控制器对比：为什么选择 ProtoMotions

发表于2026-10-08|更新于2026-10-30|理论与方法全身控制
|总字数:10.7k|阅读时长:34分钟|浏览量:

全身控制选型首先要回答：希望给机器人一条轨迹、一个稀疏目标，还是一个奖励函数？这三种输入对控制器提出的要求不同。演示视频都能让机器人走路、蹲下和挥手，不代表它们内部解决的是同一个问题。

本文把 BeyondMimic 作为动作跟踪基础，把 ProtoMotions 作为可扩展训练框架，再比较 TWIST2、SONIC 和 BFM-Zero。重点复盘 ProtoMotions 在逐际平台上的适配：哪些地方只看网络形状会漏掉错误，我在现有实现里做了什么，以及哪些问题还需要闭环实验验证。

1. 先明确比较对象：框架、策略还是集成系统

一个典型系统可以分为任务意图、运动条件、低层反馈策略和执行器四层：

任务意图 可以是“到达那里”或“把手抬高”；条件 可以是完整参考姿态、关键点、latent token； 最终还要经过关节目标和执行器模型。

框架、训练方法和集成系统处在不同层级，不能把某个系统的整套功能全部归给它的低层 actor。

2. BeyondMimic：先建立一条能解释的反馈链

BeyondMimic 适合先回答一个基本问题：在动作参考已知时，如何让带执行器约束的浮动基座机器人完成跟踪？跟踪奖励、参考初始化、自适应采样、观测和 PD 接口形成一个可以逐项检查的基础。BeyondMimic 实现

用简化目标表示：

轨迹给了策略“接下来该像什么”的密集条件。但如何为新任务产生轨迹，仍需要上层解决。跟踪器可以是通用系统的重要底座，却不能由此推导出它已经理解任意任务奖励。

这里最有价值的基线不是“能播放一个漂亮动作”，而是固定机器人和数据之后，能解释误差来自参考不可行、控制参数、观测缺失还是策略不足。没有这个基线，换成更大模型后即使失败，也很难定位原因。

3. ProtoMotions：我需要的是一条能持续修改的控制链

我选择 ProtoMotions，首先是因为已有重定向动作，接下来需要把它们变成逐际动力平台上的反馈控制。机器人模型、动作数据、观测、奖励和部署接口都要修改；如果这些改动混在一个大环境类里，每换一处就很难判断其他部分是否仍然一致。

ProtoMotions 把这些部分组织成可组合模块。我可以保留 PPO 与模拟器接口，单独替换机器人参数、参考和观测，再逐项检查动作怎样变成力矩。这个结构适合当前的适配工作，但不意味着只改一个机器人名称就能复用其他平台的策略权重。ProtoMotions 官方实现

下面讨论的是我采用的 31 自由度动作跟踪方案：actor 为 6 层、每层 1024 单元，critic 为 4 层 1024；actor 使用带噪本体状态、未来 20–160 ms 的参考和上一时刻关节目标，critic 使用更完整的仿真状态。这里的参数和改动都绑定这套实验，不代表框架所有控制器的默认设置。

3.1 同为 31 个关节，不代表控制接口相同

最容易漏掉的是：关节数正确、张量形状正确，控制含义却错了。关节数组顺序、轴方向、默认角和 PD 都会改变策略输出的作用。我在机器人适配中明确关节名称及顺序，并把默认姿态、armature、增益与力矩上限放在同一套机器人配置里；部署端再按 SDK 返回的关节名称重排状态和命令。

这套配置的髋／膝为 Kp=250、Kd=14.3，踝为 80／9.2，肩／肘为 60／3.7；相应力矩上限是 140、42、42 N·m。它们与前文 BeyondMimic 适配的增益不同，不能为了让两篇文章“参数统一”就混用。

默认角同样属于动作接口。本例肘部默认角为 −0.5 rad，另一套跟踪模型使用 +0.4 rad。若在已经确认轴方向、单位和零位相同的条件下误换默认角，关节目标会多出 0.9 rad；仅按 Kp=60 的比例项估算，就多请求 54 N·m，超过该关节 42 N·m 上限。这里说明接口错误怎样变成饱和，不是说不同模型的正负号一定有一个错误。

我的处理是让模型带着自己的机器人参数部署，而不是拿一个现成行走控制器的默认角和 PD 给它套上。SDK 能接收这些字段，只说明通信成立；参数与训练一致，才说明执行的是同一套控制规则。

3.2 动作的时间轴错了，参考、速度和前瞻都会一起错

动作数据有自己的 FPS，仿真有物理步长，策略有决策周期，SDK 又有命令发布周期。这四个时钟不能共用一个“频率”字段。

当前控制配置在 200 Hz 物理仿真下每 4 步调用一次策略，得到 50 Hz；另一条 100 Hz、decimation=2 的路径也得到 50 Hz。部署时，策略按导出参数中的 0.02 s 周期推理，SDK 可以按 1000 Hz 重复发送当前目标。提高发送频率不会让网络多看几次状态。

一个具体问题是 30 Hz、450 帧动作转换到 50 Hz。原始末帧时刻为 449/30≈14.9667 s；采用不越过末帧的采样规则，得到：

我在部署准备中按模型控制周期重采样，并按关节名称重排数据，而不是直接把 450 帧按 50 Hz 播放。后者会把动作压缩到约 9 s，速度、加速度和接触切换也随之改变。姿态插值、速度计算和身体 FK 都必须对应新的时间戳。

前瞻也以物理时间解释：[1,2,4,8] 在这里是 20、40、80、160 ms。在线参考若只有当前帧，最后三档未来信息并不会自动出现；需要上层预测、缓冲或换一种条件化训练，不能把离线跟踪结果直接当作零延迟在线控制能力。

部署循环用单调时钟计算参考帧号与下一次推理时刻，避免简单的 frame += 1 把计算耗时累积成播放减速。代价是遇到超时时可能跳过参考帧，因此还要记录实际时延和漏周期，不能只看名义 50 Hz。

3.3 仿真里看得到的状态，部署时未必有

世界位置、root 线速度和干净接触状态在仿真里很容易取到。如果 actor 依赖这些量，导出之后却只提供 IMU 与编码器，缺失的不是几个输入数值，而是训练策略所依赖的信息。

我选择的 actor 观测关闭 root 高度、root 线速度和目标 XY 偏移；critic 保留更完整的信息。部署加载器检查 ONNX 真正需要的输入，遇到要求世界位置／里程计而当前接口不能提供的模型，直接拒绝加载，不用全零占位。

另一个坑是 anchor。该策略使用腰部俯仰关节之后的躯干，SDK 的 IMU 给的是基座姿态，两者在腰部运动后不相同。我在部署端使用基座姿态与实测关节角做 FK，求出对应躯干姿态，并显式处理 SDK 的 wxyz 与模型的 xyzw 顺序。其关系可以写成：

还有一个很具体的字段问题：执行器上限字段是 effort_limit。如果读取成 effort，再把异常吞掉，导出文件就可能带着空的 effort_limits，部署端转而使用另一套限值。当前导出器读取正确字段，tracker 再检查上限数组的长度、有限值与正值，缺失或非法时停止加载。

ONNX 的 joint_pos_targets 已经包含动作映射，部署直接使用这个目标。再次执行 q₀ + scale × output，会重复施加 offset 和 scale。相关计算细节见基于 ProtoMotions 的全身控制器训练与部署。

3.5 奖励同名、权重相同，也可能学的不是同一个任务

我没有把 BeyondMimic 的奖励表原样搬来就认为任务等价。当前实验使用五个指数跟踪项、动作变化和关节限位两项代价；没有启用 anchor 位置项和非期望接触项。L2C2 则进入 actor 损失，不进入环境回报。

奖励整体尺度改变后，优势标准化也不能保证训练完全等价：critic 的回归目标、价值裁剪和熵／辅助损失的相对影响仍可能变化。我的处理是逐项核对原始量、权重、控制周期和梯度入口，再配置优化器，而不是只比较总 reward 的曲线高度。

3.6 用局部一致性处理观测扰动，不能靠部署端低通掩盖问题

L2C2 全称为 Locally Lipschitz Continuous Constraint，即“局部 Lipschitz 连续约束”：两个 L 来自 Locally、Lipschitz，两个 C 来自 Continuous、Constraint，所以也写作 L²C²。

传感噪声让相邻两次观测略有变化，如果网络输出随之大幅变化，PD 会把目标跳变变成力矩变化。我复用 L2C2 的局部平滑思路，为 actor 构造同一状态的 clean/noisy 观测对，使用共享网络比较两次输出均值。L2C2 原论文

公共 PPO 路径还有一处扩展时容易遇到的问题：主分支经过 Fabric／DDP 包装器后，再让 clean 分支经过一次同样的包装，可能触发共享 buffer 的再次广播；量化模型的 buffer 若在反传前被原地修改，会破坏第一条计算图。当前辅助前向调用解包后的同一个 actor 模块，让梯度仍流向共享参数。这不是取消分布式训练，也不是本例 MLP 已验证了所有量化模型；它是这条辅助训练路径里已有的针对性处理。

3.7 仿真和 SDK 共用推理核心，还要处理执行边界

我把 ONNX 推理、输入构造、参考采样和历史更新放进同一个 tracker，由仿真验证器与 SDK 控制器共同调用。这样先在同一组非零状态上对比输入和关节目标，再做闭环回放；可以先排除接口差异，再研究物理引擎差异。

这里取配置力矩上限的 0.95 倍。以肩部 Kp=60、Kd=3.7、上限 42 N·m 为例，当前角度为 0、速度为 2 rad/s 时，目标范围约为 [−0.542, 0.788] rad；实际下发目标再按此区间裁剪。速度不为零时区间不是以当前角度对称展开，这正是不能只做固定位置偏移限幅的原因。

这限制的是按给定 PD 公式计算的名义力矩，不是实测接触力保证；并联机构映射、执行器延迟和真实电机行为仍需验证。SDK 裁剪改变了模型原始目标，评估时还应记录裁剪比例，避免控制器长期依靠外部保护完成动作。

控制器同时检查关节顺序、反馈有限值和传感器时间戳。关节／IMU 时间戳超过 0.3 s 不更新时，进入故障分支，关闭位置增益并尝试受限阻尼；反馈非法、无法构造有效命令时停止该控制器的发送。0.3 s 是当前故障检测设置，不是经过认证的安全时限，软件检查也不替代机器人本身的急停与驱动保护。

3.8 起步、收尾和接触，仍然不能由框架替我解决

从参考中间帧开始跟踪，与从任意站姿切入整段动作是两个任务。当前 stand 控制器从实测关节角出发，用 3 s 的 smoothstep 过渡到站姿；但切到 tracker 后，仍直接从动作第 0 帧启动。这一步没有自动完成站姿到动作首帧的平滑衔接。

动作结束后，当前实现继续以实际状态运行策略、跟踪末帧，直到切换控制器，并不是冻结最后一次输出力矩。如果末帧不是可持续站立姿态，继续跟踪末帧也不等于已经解决停止问题。起步和收尾需要检查姿态、速度、支撑与接触；仅把关节位置插值平滑，仍可能构造出不可执行的参考。

物体交互则是另一条尚需扩展的任务链。当前七项环境奖励没有物体状态、夹持预紧和接触丢失目标，也没有在线导纳参考。将自由空间动作跟踪得很好，不能据此宣称已经具备柔顺交互。后续需要接入物体与接触状态、受力参考和对应奖励，具体机制见柔顺交互篇。

现有工程记录注明：已经做过模型数值一致性、单轨迹 MuJoCo 闭环和离线 SDK 检查，尚未在物理机器人上运行这条跟踪链。本文据此讨论已实现的接口与保护，不把代码里存在某个模块写成真机性能已经改善。

7. 这些 latent 不能仅凭名称类比

SONIC 的共享表示强调统一运动条件入口；BFM-Zero 的 latent 与任务目标及价值表示关联；ProtoMotions 中某个实验是否存在 latent、如何训练它，要由该实验定义。三者都出现向量 ，并不意味着它们优化相同目标。

一个简单鉴别方法是问：修改 的某一方向，预期改变什么？如果答案是改变编码后的运动模式，就应评估动作覆盖与条件重建；如果答案是改变被优化的任务目标，就应评估目标/奖励推断与组合性能。不能只画 latent 插值动画，就宣称拥有任意任务控制能力。

同样，模型支持动作跟踪，不表示它会适度降低夹持力；存在柔顺演示，也不表示它满足可计算的接触力界。这些能力需要对应的观测、训练分布和评估协议。

奖励与目标函数：框架相近，优化对象未必相同

BeyondMimic 与本文 ProtoMotions 实验的环境项分别为“六个跟踪项＋三项正则”和“五个跟踪项＋两项正则”。后者没有配置 anchor 位置／非期望接触项，动作平滑的数学形式也不同；完整系数分别见基础篇的奖励表与ProtoMotions 奖励表。比较学习算法前，应先对齐这些任务定义。

逐项实现

penalty_torques

原始值是所有关节力矩平方和。很小的数值仍可能产生明显贡献，因为力矩带物理尺度且按关节累加。不能把 −1e−6 与有界指数跟踪项的 1.0 直接比较。

penalty_undesired_contact

运动环境覆盖了基础实现：只要指定身体中任一接触力分量的绝对值大于 1 N，就返回 1，而不是按接触身体个数相加，也不是力范数阈值。

penalty_action_rate

相邻动作的平方和，没有除控制周期。它约束控制输出，不是 FB 表示损失；动作到 PD 的缩放仍会改变物理影响。

penalty_ankle_roll

运动环境单独读取左右 ankle roll 角度并平方相加。该项并非跟踪参考脚踝角，而是偏向 roll=0；过强可能限制合法的侧向姿态。

penalty_feet_ori

将重力方向旋转进各脚坐标系，取水平分量的范数；只在对应脚 z 向接触力 >1 N 时生效。它不是直接罚脚的三个欧拉角。

feet_heading_alignment

分别计算左右脚与 root 的 yaw，用 wrap_to_pi 得到最短角差，取绝对值求和。虽然系数为负，此项不在课程惩罚名单，因此不乘该课程系数。

penalty_slippage

实现是接触门控的三维足部线速度范数之和，不是水平速度平方；接触门限使用力范数 >1 N。只凭 slippage 名字不能判定各论文测量的是同一量。

limits_dof_pos

上下软边界之外的线性距离按关节求和。配置软位置比例为 0.95；软限位课程默认关闭，与奖励惩罚课程是两个独立开关。

limits_dof_vel

超过 0.95 倍速度上限后产生代价，每关节越界量最多计 1 rad/s。这项没有列入当前 reward_penalty_reward_names，所以从开始就使用完整的配置权重。

limits_torque

当软力矩限位课程关闭时，源码对超过 0.95 倍上限的部分取正部并求和，没有每关节 max=1 裁剪；不能与速度项写成完全相同的函数。

为什么十项辅助代价还不是 BFM 的“任务”

辅助 critic 让动作保持在机器人可以承受的范围内，但“向前走还是向后走”由行为条件与任务提示决定。不能把十项物理代价求和后称为完整的 FB 目标，也不能把推理时用户写的奖励当成每次都要重新训练 actor 的奖励。表示学习把任务到 latent 的映射提前准备好，推理再通过状态样本与任务评分选择条件。

这与 ProtoMotions 的差异是工程取舍：当前显式参考策略的输入、误差和 PD 契约更容易逐项审计；BFM 路线增加表示覆盖与 latent 推断这层需要验证的对象。本文没有对 BFM-Zero、SONIC 或 TWIST2 做目标机器人的移植或同机复现，因此不把它们的官方配置写成“当前适配后的参数”，也不虚构一套统一奖励权重。对 SONIC 和 TWIST2 的比较限定在官方说明的系统接口；它们的不同训练阶段应各自绑定配置后再做数值对照。

8. 这些改动为什么让我继续选择 ProtoMotions

如果目标只是验证一段动作在固定机器人上能否跟踪，BeyondMimic 的基础链已经很有价值。我继续选择 ProtoMotions，是因为接下来要反复修改数据、观测、策略结构和执行方式：扩大动作覆盖、处理传感扰动、比较不同参考条件，再接入物体与接触。需要持续改变的是整套实验，而不只是一个 actor。

前面的改动正好对应这些迭代边界。机器人配置固定关节与执行器含义；参考采样器固定物理时间；观测组件划清本体感知与特权信息；动作模块与导出校验约束网络输出的解释；共享 tracker 把仿真和 SDK 连接起来。L2C2 复用已有方法，部署检查处理接口错误，它们都不是“换成 ProtoMotions 就自动获得”的能力。

这些工作降低的是错误定位与接口重写的成本。例如目标角差四倍，可以先查 scale 和导出映射；腰动时姿态突然不对，可以查 anchor 与 FK；回报尺度不同，可以回到具体奖励汇总。是否提高了成功率、是否真的更省训练预算，仍需要固定协议的实验，不能用工程结构更清楚代替性能数据。

代价也很明确：我仍然要维护模型参数、动作转换与导出约定；当前控制器依赖完整的未来参考；起步收尾、跨引擎接触和真实执行器行为没有因为模块化而消失。自由空间动作训练也不能直接解决物体交互。选这个框架，是因为这些问题可以在明确的组件边界上继续改，而不是因为它已经替我解决了它们。

若主要目标变为在已有支持平台上统一多种运动输入，SONIC 的入口值得评估；若核心问题是不为每个新目标重新训练、通过奖励提示控制行为，BFM-Zero 更直接对应任务。当前最先需要补齐的是目标机器人的参考—状态—执行器闭环，因此我把 ProtoMotions 作为后续全身控制与交互实验的载体。

第三组是资源与迁移：训练交互步数、GPU 小时、推理时延分布、导出后的依赖，以及新增机器人必须重做哪些数据和模块。公开数据与自采数据应分开统计，不能只报告网络参数量。

本文给出基于接口与训练目标的选型分析，尚未完成同机器人、同动作测试集的统一性能基准。

一个可检验的选型结论应当能够被实验推翻：如果在相同预算与接口条件下，另一条路线显著降低适配成本并提高目标任务成功率，就应调整选择。选择 ProtoMotions 的理由是当前问题与其模块化跟踪流程匹配，而不是认为框架名称本身意味着更强控制能力。
